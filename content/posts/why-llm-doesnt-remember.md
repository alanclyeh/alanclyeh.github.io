*這是《AI Agent 是怎麼跟 LLM 講話的》系列第 2 篇。[上一篇](../minimal-ai-agent-in-30-lines/)做了一支三十幾行的 agent，它能聊天，但不記得上一句。*

先把現象重現一次：

```text
你 > 我叫小明。

模型 > 你好，小明！很高兴认识你。有什么我可以帮助你的吗？
[送出 558 tokens，回答 71 tokens]

你 > 我叫什麼名字？

模型 > 我無法知道你的名字，因為你在對我說話之前並沒有告訴我。
[送出 561 tokens，回答 60 tokens]
```

同一支程式、同一個模型、中間隔不到十秒鐘，它就是不知道。

## 先排除幾個直覺的猜測

大部分人第一反應會是下面這三個，我們一個一個試。

**「是不是模型太小？」** 不是。我另外抓了 `gemma3:4b`、`llama3.2:3b`、`ministral-3:3b` 問同一題，四顆模型的反應一模一樣 —— 沒有一顆知道上一句是什麼。換成雲端那些幾百 B 的大模型，結果也不會變。

**「是不是要拜託它記得？」** 試試看把話講明：

```text
你 > 我叫小明，請記住我的名字。

模型 > 好的，小明！我已經記下了你的名字，以後在對話中會稱呼你「小明」哦～有什麼我可以幫忙的嗎？

你 > 我剛剛叫你記住的名字是什麼？

模型 > 我沒有記憶功能，每次對話都會從頭開始。這次你剛剛沒有給我任何需要記住的名字，所以我無法回應。
```

它上一句才剛說「我已經記下了」，下一句就說「你剛剛沒有給我任何需要記住的名字」。

這兩句話不衝突 —— 因為對它來說，那根本是兩件互不相干的事。

**「是不是 Ollama 的問題？」** 也不是。這跟 Ollama 無關，換成主流的雲端 chat API，行為完全一樣。有些服務另外提供「在伺服器端幫你存對話」的選項，但那是在模型外面另外包的一層 —— 模型本身還是每次都從頭讀一整份稿。

## 真相在自己的程式裡

回頭看上一篇的 `ask()`：

```python
def ask(question):
    body = {"model": MODEL, "stream": False,
            "messages": [{"role": "user", "content": question}]}
    ...
```

`messages` 裡面**永遠只有當下這一句**。

上一篇拆過那包 JSON：它是一個一次性的 HTTP 請求，打完就結束，伺服器那端什麼都沒留。所以模型每一次收到的，就真的只有我們送過去的那幾個字 —— 它不是「忘記」，是**從來沒有拿到過**。

講白一點：

> **LLM 沒有記憶這個功能。它只會把你送過去的東西讀完，然後接著寫下去。**

那市面上那些記得住對話的 AI 是怎麼做的？答案很無聊：**每一輪都把整串歷史重送一遍。**

## 動手修：關鍵只有兩行

把 `messages` 從函式裡面搬出來，變成一個活在迴圈外面的 list：

```python
def ask(messages):                    # 收整串，不是收一句
    body = {"model": MODEL, "stream": False, "messages": messages}
    ...


messages = []                          # 這個 list 就是「記憶」

while True:
    question = input("\n你 > ").strip()
    ...
    messages.append({"role": "user", "content": question})
    reply = ask(messages)
    answer = reply["message"]["content"]
    messages.append({"role": "assistant", "content": answer})
    print("\n模型 >", answer)
```

關鍵是最後那兩個 `append`：**使用者說的話要存，模型說的話也要存。**

### `assistant` 這個 role 的用途

上一篇列過 `role` 有三種，當時只用到 `user`。現在 `assistant` 出場了，而它的用途有點反直覺：

**我們要替模型「複述」它自己說過的話。**

模型那端什麼都沒留，所以「你上一輪回答了什麼」這件事，也得由我們送回去告訴它。整串 `messages` 送出去之後，模型讀到的是一份完整的對話逐字稿，然後接著往下寫。

它不是在回憶，它是在**讀稿**。

再跑一次，一模一樣的兩句話：

```text
你 > 我叫小明。

模型 > 你好，小明！很高兴认识你。有什么可以帮助你的吗？
[送出 558 tokens，回答 65 tokens，對話已有 2 則訊息]

你 > 我叫什麼名字？

模型 > 你自己刚刚告诉我你叫**小明**哦～
[送出 633 tokens，回答 42 tokens，對話已有 4 則訊息]
```

關鍵的改動就是那兩個 `append`，整支檔案只多了幾行。

差別一樣寫在數字裡：第二輪送出去的從 561 變成 **633**。多出來的七十幾個 token，就是第一輪的問答被原封不動塞回去了。

## 代價一：每一輪都在變貴

既然每輪都要把整串重送，那送出去的東西就會一路變長。上一篇印出來的 token 數字，現在派上用場了。

連續聊六輪，每輪都講一句很短的話，看 `prompt_eval_count`（送出去的 token）怎麼變化：

```text
第 1 輪  送出   558 tokens   「我叫小明。」
第 2 輪  送出   645 tokens   「我養了一隻叫咪咪的貓。」
第 3 輪  送出   965 tokens   「咪咪三歲了。」
第 4 輪  送出  1967 tokens   「我在學 Python。」
第 5 輪  送出  3076 tokens   「我最近在寫一支聊天程式。」
第 6 輪  送出  4031 tokens   「我的貓叫什麼名字？」
```

六輪，送出去的東西漲了七倍多。

而我每一輪講的話都不超過十五個字 —— 漲的不是我說的，是**模型自己講過的話**。它每次都回一大段，那些全部要原封不動送回去。

（第 1 輪那個 558 是[第一篇](../minimal-ai-agent-in-30-lines/)挖出來的內建 system prompt，是固定的底，跟對話長短無關。）

順帶一提，第 6 輪它答對了：

```text
模型 > **咪咪！**（你的貓咪的名字就是咪咪！）
```

四輪之前講過的事，它記得 —— 因為那五輪全部都在剛剛那 4031 個 token 裡面。

雲端 API 是按 token 計費的，所以一段長對話的成本不是線性的 —— **每多講一輪，之前講過的全部都要再付一次錢。**

多數雲端 API 有 prompt caching，重送的舊內容會打折計費，便宜一些，但還是得整串送、還是要付錢。

本機跑的話不用付錢，但要付時間：送出去的 token 越多，模型讀完的時間就越久。

## 代價二：塞不下的時候會怎樣

每個模型都有 **context window** —— 一次最多能讀多少 token。塞爆了會怎樣？

為了快速看到現象，把它縮到很小（正常情況不會這樣設）：

```python
body = {"model": MODEL, "stream": False, "messages": messages,
        "options": {"num_ctx": 1024}}     # 故意設得很小
```

`1024` 這個數字是刻意挑的：內建的 system prompt 就佔掉 558，所以真正留給對話的只剩四百多個 token，聊三輪就會滿。

先告訴它一個名字，接著聊幾輪不相干的，最後再問它名字：

```text
你 > 我叫小明，請只回「好」。
模型 > 好。
[送出 565 tokens]

你 > 用三句話介紹咖啡有哪些種類。
模型 > 1. 濃縮咖啡（Espresso）……
[送出 583 tokens]

你 > 再用三句話介紹沖煮方式。
模型 > 1. 濾杯沖煮……
[送出 791 tokens]

你 > 再用三句話介紹烘焙程度。
模型 > 1. 淺度烘焙（Light Roast）……
[送出 836 tokens]

你 > 我叫什麼名字？
模型 > 我無法知道你的名字，因為這是一個新的對話，且我沒有記憶功能來跟踪個人資訊。
[送出 821 tokens]
```

注意最後一行：**送出去的 token 從 836 變成 821，不升反降。**

我的程式沒有刪任何東西，`messages` 裡「我叫小明」那句還好好的。是 Ollama 在送進模型之前，把裝不下的部分從最前面整則丟掉了。

而它回的那句「這是一個新的對話」，從它的角度看完全正確 —— 它收到的那份逐字稿，開頭已經是咖啡了。

在 Ollama 上，它不會報錯，也不會說「我塞不下了」。**它就只是安靜地忘掉最前面的東西。**

雲端 API 則多半相反：超過 context window 會直接回錯誤、拒絕這個請求，不會替你裁掉。兩種都得由 agent 程式自己處理。

### 所以真實產品怎麼處理

知道了這個限制，那些看起來很神秘的設計就都有解釋了：

- **只保留最近 N 輪** —— 最簡單，但會突然失憶
- **把舊對話做成摘要** —— 讓模型自己把前面幾十輪壓成一段話，再放回 `messages` 開頭
- **把該記的東西存到外面** —— 存進資料庫或向量庫，需要時才撈相關的幾段塞進去（這就是 RAG 的起點）

這些手法沒有一個是模型提供的功能，**全部都是 agent 程式自己在做。**

## 小結

- LLM 沒有記憶，它只會讀你送過去的東西
- 「對話」是你的程式每輪把整串歷史重送一遍做出來的
- `assistant` 這個 role 的用途，是替模型複述它自己說過的話
- 重送要付代價：token 一路變長，錢和時間都會漲
- context window 塞爆時，Ollama 不會報錯，只會安靜地忘掉最前面；雲端 API 多半直接拒絕
- 所謂「記憶管理」，管的就是 `messages` 這個 list

現在它記得住對話了。但它是誰？什麼都能聊，代表什麼都不夠專精 —— 下一篇只要多一則訊息，就能把它變成專門做一件事的 agent。
